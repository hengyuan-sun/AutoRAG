# 开源产品与文档切分评测调研

调研日期：2026-10-22。服务于本项目“文档处理研发工作台”的选型，范围涵盖开源产品、切分组件、开放数据集及可复现指标。资料来自官方仓库、作者论文和发布方数据卡；本次未安装对比产品、未下载完整数据集、未实际跑分。下文“推荐”和平台新增指标为本项目判断，与来源方已有能力区分说明。

## 1 调研结论

建议继续采用RAGFlow作为解析与结构处理基础，自建试验、评测和发布控制层。重点借鉴AutoRAG旧版的配置搜索、Haystack的组件评测、Onyx的企业连接器与权限元数据设计；切分实现优先评估Chonkie和Docling，避免从头实现所有算法。

切分效果应分四层评估：解析是否正确、切分边界与结构是否合理、证据是否高效召回、最终答案是否正确。首期以“证据区间召回 + 上下文精度 + 检索排序 + 处理成本”为主，不依赖通用生成模型或LLM评审。

首批推荐数据组合为LegalBench-RAG、QASPER和企业自建中文证据集；Chroma chunking_evaluation用于指标与数据生成方法对照。HiCBench与本平台目标高度匹配，但本次作者提供的HF地址未能读取，须先验证发布包、字段和许可再列入默认套件。CRUD-RAG作为中文端到端补充，OmniDocBench/OHR-Bench作为解析诊断补充。

不存在一个公开数据集可以同时完整验收中文企业工艺、复杂表格、同名文件版本、权限和文件流更新；最后三项尤其需要本项目自己的可控测试。

## 4 指标体系

### 4.1 三种评测不能混淆

1. 解析评测：固定文档，比较解析器是否保留文字、表格、结构与定位。
2. 切分评测：固定解析后的规范化原文，比较边界、完整性及证据保留。
3. 检索评测：固定Embedding、索引、检索参数和问题，对不同切分产生的索引做对照。

更换解析器和切分算法一起测属于端到端方案比较，应单独标识。只有固定其他因素，才能把结果变化合理归因于切分。答案生成另加第四层，首期没有通用生成模型也能完成前三层。

### 4.2 原文证据区间指标

平台主口径建议使用“文档ID + 版本 + Unicode码点位置”的字符区间，内部用左闭右开[start,end)。英文公开基准另外实现固定Tokenizer的Token口径；字符分数与Token分数分栏，不能混合平均。位置指原文出现位置，不是不同词语的集合，相同词在不同位置不能互相算命中。

对每题定义：G为全部黄金证据位置的并集；U为实际交付下游上下文覆盖的唯一原文位置；T为交付文本的字符/Token总数，重复内容重复计数。

| 指标 | 平台建议定义 | 含义 |
| --- | --- | --- |
| Evidence Recall | count(G∩U) / count(G) | 证据是否取全 |
| Evidence Precision unique | count(G∩U) / count(U) | 去重上下文中有多少是证据 |
| Evidence IoU unique | count(G∩U) / count(G∪U) | 兼顾漏召回和无关上下文 |
| Effective Evidence Precision | count(G∩U) / T | 将实际重复传输纳入Token效率成本 |
| Context Redundancy | 1 - count(U) / T | 同一原文内容重复交付比例 |

这些“unique/effective”名称和组合为平台建议口径。Chroma技术报告提出Token级Recall、Precision及IoU，并针对重复检索有专门计数方式；若复现其结果，应另注册chroma-compatible指标严格遵循其代码，不能把上述自定义unique版本声称为论文原式。参考：[Chroma技术报告](https://www.trychroma.com/research/evaluating-chunking)。

例：黄金证据100 Token，最终取到80个唯一证据Token，唯一上下文共200 Token，含重叠后实际交付250 Token。则Recall=0.80，unique Precision=0.40，unique IoU=80/220≈0.364，effective Precision=0.32，冗余率=0.20。

synthetic修订、重复表头、父块合并与无来源说明文字不能虚构原文位置。人工新增上下文会计入T，但没有真实映射便不增加证据命中。父子检索必须按真正返回的父块/合并块计算U和T，不能只按命中子块计算成本。

### 4.3 边界与结构指标

| 指标 | 需要的标签 | 使用方式及限制 |
| --- | --- | --- |
| Boundary Precision / Recall / F1 | 句子间或块间的黄金切分点 | 精确匹配为主；如增加±1句容差，用一对一匹配并独立命名，禁止一个预测点重复命中多个真值 |
| 层次Boundary F1 | 各层黄金切分点 | 每层单报及忽略层级合并结果；可对照HiChunk论文的L1/L2/Lall，不拿单层结果冒充层次能力 |
| Pk ↓ | 同一原文序列的参考分段 | 检测固定间隔两点是否被错误判为同一段/不同段；窗口和粒度固定 |
| WindowDiff ↓ | 同上 | 比较滑动窗口内预测与参考边界数量差异；近边界偏移比纯Exact F1更有解释空间 |
| 结构破坏率 ↓ | 标题/表格/条款等结构标签 | 平台自定义：被切断的受保护结构数/结构总数；必须预先定义“允许跨块”的规则 |
| Evidence Fragmentation ↓ | 黄金证据span | 平台自定义：覆盖同一证据所需的最少输出块数；需同时报告未完全覆盖比例，不能只看已覆盖样本 |

参考：[HiChunk论文](https://arxiv.org/abs/2509.11552)、[WindowDiff原论文](https://aclanthology.org/J02-1002/)、[SegEval实现](https://github.com/cfournie/segmentation.evaluation)。边界正确不保证检索最优，固定长度分块也不应仅因未遵守章节边界就被一票否决。

无需标签的工程诊断包括：空块率、长度P50/P95/最大值、超模型Token上限率、原文内容覆盖率、重复率、解析/切分秒数、向量数量和索引存储。块内余弦相似度等语义一致性分数可以辅助解释，但同样依赖Embedding，不能单独作为“切分质量总分”。

### 4.4 检索排序与结果指标

| 指标 | 定义与注意事项 |
| --- | --- |
| Document Recall@K | TopK去重文档中相关文档数/相关文档总数；明确如何从块排名聚合文档排名 |
| Hit@K | TopK中至少命中一个相关目标为1，否则0，再按题平均 |
| MRR@K | 第一个相关目标排名倒数，未命中为0 |
| nDCG@K | gain=2^grade-1，discount=log2(rank+1)，除以理想DCG；需要相关等级或明确二值约定 |
| All-evidence Success | 平台自定义：该题要求的全部证据是否均达到预设覆盖阈值；对跨条款/跨表格问题比Hit更严格 |
| P50/P95/错误率 | 检索、重排、模型加载分阶段统计，失败和超时保留，不通过删样本美化结果 |

跨切分不要以Chunk ID作为共同真值；用稳定原文证据对齐。只有问题提供文档标签时报告文档级指标，不能自动推导字符级黄金标签；只有答案字符串也不能证明检索已取回全部证据。

最终生成评测可增加Answer EM/F1、引用正确性、事实覆盖和Faithfulness，但不能用ROUGE/BLEU替代证据召回，也不能把Ragas基于参考答案/模型判断的Context Recall混称为本平台基于明确区间的Evidence Recall。

## 5 公平实验设计

### 5.1 两条独立比较轨道

- 固定K：K=3/5/10，对照块级排序、文档召回和噪声；同时显示实际返回Token数。
- 固定上下文预算：例如512/1024/2048 Token，按固定排序装配上下文，对照Evidence Recall、Precision、IoU与成本。预算值为建议实验点，不代表本地模型最佳值。

固定预算轨道是比较切分大小的关键。大块在同一TopK下返回更多文本，可能靠体积提高Recall。不得仅凭Recall@5就选出最优块长。截断/跳过超大块的装配规则必须固定，并对实际交付文本重新计分。父子检索必须先完成父块合并去重，再按真实交付结果计预算。

为区分切分能力与检索失败，可额外报告Oracle Evidence Ceiling：在同一语料块集合和预算内，使用已知黄金证据选择块所能达到的覆盖上限；该值只作诊断，不参与正常检索排名，也不能伪装成实际召回。

### 5.2 控制变量

固定源文档hash与版本、解析快照、查询集合、Embedding digest、查询前缀、向量维度、距离、全文分词、检索/融合参数及重排开关。初期使用pgvector精确检索减少ANN因素，后续用同一切分再独立比较HNSW和Milvus。存储切换实验与切分实验不同时改变变量。

本地首轮使用已验证的qwen3-embedding:0.6b，先关闭尚未完成协议验证的Reranker。对400/800/1200字符、0/100重叠等做小规模试验，精确记录字符设置和实际Token分布；不把字符长度直接视为Token长度。

结果按语言、格式、单证据/多证据、表格、长文档分组。总表对每个数据集先单独汇总，不把几十万企业文档和几十道法律题简单混成一个总分。报告有效题数、错误数、95%配对bootstrap区间；存在同文档多题时以文档为重采样簇，避免把高度相关的问题当独立样本。

调参集和最终验收集按文档拆分，并处理近重复；不能让同一文件不同版本分别落入开发和测试而产生泄漏。无答案题独立评估，在向量检索永远返回K条的设置下，“非空结果”不等于错误回答，需要明确拒答/阈值策略。

## 6 平台数据契约与页面建议

统一基准包包含corpus.jsonl、queries.jsonl、qrels.jsonl、evidence_spans.jsonl及manifest.json。原始数据只读缓存，转换产物另存。manifest登记dataset_id、来源URL、revision、license、split、文档/问题数量、文本hash、normalize_version、tokenizer及标注粒度。

每条证据记录doc_id、document_revision、block_id、start、end、unit、evidence_group_id及alignment_status。明确source_document、normalized_text和block坐标之间的映射。格式清洗必须输出offset map；精确匹配失败记录unaligned并进入人工核对，模糊匹配置信度不足时不强制打分。

每个数据集适配器声明能力：has_document_qrels、has_exact_spans、has_boundaries、has_layout、has_answers、language。评测页面仅开放其支持指标。标签缺失显示N/A，不能显示0或自行生成未经确认的标签。

新增页面区域建议：

1. 基准库：来源、版本、许可状态、样本量、标签粒度、下载/对齐状态。
2. 实验矩阵：策略、长度、重叠、固定K/预算、模型digest及检索方式。
3. 对比看板：Evidence Recall—Precision散点、预算—召回曲线、延迟—效果Pareto前沿。
4. 逐题证据查看：原文高亮黄金证据、命中部分、漏掉部分及重复上下文。
5. 发布门槛：相对基线回归、关键类别下限、错误率、越权和可重放检查。

不建议将所有指标任意加权成“总分第一名”。在Recall门槛和安全条件满足后，比较精度、延迟、存储及人工可解释性，以Pareto候选形式让研发选择。

## 7 推荐落地顺序

| 阶段 | 工作内容 | 产物与通过条件 |
| --- | --- | --- |
| R0 数据核验 | 检查LegalBench-RAG、QASPER、Chroma的数据入口、许可、文件和offset一致性；HiCBench另核验可获取性 | 版本化manifest及能力矩阵；未通过者不能默认导入 |
| R1 确定性指标 | 实现字符区间Recall/Precision/IoU、冗余、文档Recall/MRR和固定预算装配 | 手工构造含重叠/重复/跨文档的例子验证精确值，无需生成模型 |
| R2 三组基线 | 递归、滑动窗口、标题结构，同源快照、相同本地Embedding与精确检索 | 固定K与预算双轨结果，错误题不被丢弃 |
| R3 企业中文黄金集 | 选30–50份经授权文件，人工标注100–200题，覆盖工艺条款/表格/多证据/无答案 | 文档级开发/测试拆分，两人复核关键证据；公开基准成绩不能替代此验收 |
| R4 增强策略 | 父子/表格/语义切分、重排及OCR对照 | 逐因素增加，不同时更换模型与存储 |
| R5 发布门槛 | 将选定基准、阈值、配置和报告绑定release | 候选版本自动执行固定回归，记录可解释的通过或拒绝原因 |

30–50份、100–200题是本项目的起始采样建议，不是已有数据或统计充分性承诺。先用固定小子集打通数据适配，再扩大规模；不要首轮将8万新闻或50万企业模拟文档全部灌入本机。

## 8 对现有方案的补充结论

当前架构不需要因本次调研重选数据库或引入第二套平台。建议在既定网关中增加DatasetAdapter、MetricRegistry、ContextAssembler和EvidenceAligner四个边界，并把基准manifest、精确证据offset、Tokenizer版本与预算策略加入实验及发布快照。

第一优先级从“展示Recall@5”提高为“原文证据可对齐、固定预算公平比较、逐题可追溯”。只有这三点落实，策略预设和参数扫描才能成为研发工具的实质能力。
